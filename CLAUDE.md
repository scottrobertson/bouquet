# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Bouquet is a self-hosted IPTV playlist manager. You add Xtream Codes providers (sources), merge their channels into curated playlists through a web UI, and it serves back an M3U playlist plus a matching XMLTV EPG. It is a playlist manager, not a proxy: output M3U files contain the provider's own direct stream URLs, the video never passes through Bouquet.

It's two halves: a Rust server in `server/` (axum + SQLite) that owns all data and logic, and a React Router 7 web app in `app/` that runs only in the browser and talks to the server's JSON API. Production is one binary with the built web app embedded in it.

## Commands

Server (run from `server/`):
- `cargo run` — the server on :3000. Debug builds read the web app from `../build/client` and don't run the scheduler.
- `cargo test` — all server tests. Also writes the TypeScript API types to `app/api/types/` (ts-rs), so run it after changing any type the API sends.
- `cargo test sync::` — tests in one module; `cargo test reorder` filters by name.
- `cargo clippy --all-targets -- -D warnings` — lint, as CI runs it.
- `cargo build --release` — the production binary, with `build/client` embedded. Run `npm run build` first.

Web app (run from the repo root):
- `npm run dev` — starts both: Vite on :5173 and `cargo run` on :3000, under watchexec so the server rebuilds and restarts when Rust code, migrations or `Cargo.toml` change. `npm run dev:web` or `npm run dev:server` runs just one. Vite passes `/api`, `/events`, `/output`, `/img` and `/settings/backup` through to the server (`BOUQUET_API_URL`, default `http://localhost:3000`).
- `npm run build` — static files into `build/client`.
- `npm run typecheck` — `react-router typegen` then `tsc`, against the generated API types.
- `npm test` — Vitest, for the logic the browser runs itself.

Before starting `npm run dev`, check whether ports 5173 and 3000 are already in use (`lsof -i :5173 -i :3000`). The dev servers are often already running in another terminal tab. If they're up, use those instead of starting a second pair.

CI (`.github/workflows/ci.yml`) runs typecheck and Vitest, clippy and `cargo test`, checks the generated API types are committed, then builds and boots the Docker image.

## Where things live

- `server/src/routes/` is the HTTP layer. `mod.rs` wires every route; each page has a module (`sources.rs`, `playlists.rs`, `editor.rs`, `guide.rs`, `settings.rs`) with a GET for its data and a POST for its form actions, at `/api` plus the page's path. `output.rs`, `img.rs`, `events.rs` and `static_files.rs` serve everything else. Route handlers stay thin and call into the modules below.
- `server/src/` holds the logic, one module per area: `sync`, `probe`, `output`, `playlist` (`mutations.rs`, `queries.rs`), `guide`, `upload`, `backup`, `sources`, `xtream`, `scheduler`, `events`.
- `server/migrations/0001_baseline.sql` is the schema, commented. It's the best map of how a feature hangs together.
- `app/routes.ts` is the page map. Each route file has a `clientLoader`/`clientAction` that call `apiLoad`/`apiAction` from `app/lib/api.ts`.
- `app/api/types/` is generated by ts-rs from the Rust response structs. Don't edit it by hand.
- `app/components/<area>/` groups UI by screen: `playlist/` (the editor), `guide/`, `sources/`, `playlists/`. `app/components/ui/` is generated shadcn/ui, leave it alone unless adding a new shadcn component.
- `app/lib/` is browser-side helpers: the API client, alt naming, smart sort, channel matching, quality labels, dnd sensors, the live revalidate hook.
- `test/` holds the Vitest tests for `app/lib`. Server tests sit next to their code in `#[cfg(test)]` modules, with shared fixtures in `server/src/test_support.rs`.
- `data/` holds the runtime SQLite db and backups in dev/prod. Tests never touch it; they use in-memory or temp-dir databases.
- The dev database in `data/` usually has real sources and playlists in it, so it's often quicker to look at real behaviour through the running app than to construct test data.

## Architecture

**API shape.** Every page's loader and action is one Rust handler pair. Forms post URL-encoded (`apiAction` converts FormData), read on the Rust side with `routes/form.rs`, which works like FormData (`get`, `all`, `ints`). Actions branch on an `intent` field and return JSON with the status the page expects; a 4xx stops React Router reloading the page's data. A redirect comes back as `{ "redirect": "/path" }`. Dates go over the wire as ISO strings (`api::iso`), and text columns with a fixed set of values get exact TypeScript types through `api::kinds`.

**Data model (`server/migrations/`).** The core flow:
- `sources` are providers. `source_channels` / `source_epg_channels` / `source_categories` / `epg_programmes` are the raw catalog pulled from a source on sync. This is the source of truth and is keyed so resync never disturbs user edits.
- `playlists` → `playlist_categories` → `playlist_channels` are the curated output. A `playlist_channel` points at a `source_channel` and carries per-playlist overrides (custom name, logo, EPG, position, enabled). Edits reference the stable `source_channel_id` so they survive resync.
- **Alternates**: a `playlist_channel` with `primary_channel_id` set is a backup/duplicate grouped under another channel. They still emit as separate channels in the M3U; grouping is purely an editor/naming convenience. See the README's "Alternates" section and `server/src/alt_name.rs`.
- An "auto-sync group" is a `playlist_category` with `auto_source_id` set: it mirrors a source category live and has no `playlist_channels` rows.

**Schema changes (`server/src/db.rs`).** SQL files in `server/migrations/`, embedded in the binary and run in order on startup, with the version in SQLite's `user_version`. The baseline counts as version 25, carrying on from the TypeScript app's drizzle migrations, and a database the TypeScript app left at 25 is adopted as it is. To change the schema, add `0002_<name>.sql` and list it in `MIGRATIONS`. Restore copies tables with `SELECT *`, so new columns must be added the same way for old backups and new databases alike.

**DB connection (`server/src/db.rs`).** One rusqlite connection behind a mutex, in WAL mode with foreign keys on. Async code reaches it with `db.call(|conn| ...)`, which runs on a blocking thread; don't call `db.lock()` from async code, since a long sync transaction would stall the runtime. Id lists go into queries as one parameter with `IN rarray(?)` and `db::id_array`.

**Sync (`server/src/sync.rs`).** Pulls the catalog and per-channel EPG from the Xtream API (`xtream.rs`). EPG comes from `get_simple_data_table` per channel (includes aired programmes, unlike xmltv.php), fetched with a concurrency pool. Each source has its own `sync_interval_minutes`. Every sync also records a diff (channels added/removed/returned, categories) via `sources/changes.rs`, shown on the source's Changes page. Provider JSON is loosely typed, so `js.rs` reads values the way JavaScript's Number() and String() do.

**Output (`server/src/output/`).** `output/m3u/:token` and `output/epg/:token` are public, unauthenticated routes hit by IPTV players, keyed by a per-playlist `output_token`. Results are cached (`cache.rs`), invalidated on sync and edits. `resolve.rs` turns a playlist into its final channel list (overrides applied, alternates named, auto groups expanded); the M3U and XMLTV builders and the guide all feed off it, so output-shape changes usually go there.

**Uploads (`server/src/upload/`).** A playlist can have upload destinations (local path or S3) that get the freshly built M3U + EPG pushed to them after a sync, debounced so one cron tick uploads once. All storage-library specifics stay in `storage.rs` behind `UploadTarget`.

**Probing (`server/src/probe/`).** Runs ffprobe against streams to record quality (resolution, frame rate, codecs, bitrate) shown in the editor. Each probe opens a real connection to the provider, so the scheduled probe only covers channels actually in output (enabled, available, not in a disabled category). Manual probes (single channel, or "Probe enabled") use a wider net, but still only cover switched-on channels, so auto-disabled ones have their own action. Bitrate can't be read from a live stream, so measuring it reads the stream for the read time and weighs the data (off by default, it's slow). Probing can also flag all-black streams: it decodes a few seconds with ffmpeg's blackdetect and marks the channel failed if the picture is all black (on by default), catching dead channels that still look fine to ffprobe. The external programs sit behind the `Tools` trait so tests can stand in for them. Binaries come from `FFPROBE_PATH`/`FFMPEG_PATH`.

**Scheduling (`server/src/scheduler.rs`).** Runs sync, probe and backup on their cron expressions inside the server process, calling the same functions the UI does. Release builds only. The ticks are hourly and each job only acts on sources whose interval has passed; a tick is skipped if the previous run is still going.

**Live updates (SSE).** Background sync/probe/upload runs tell open browser tabs about progress through an in-memory broadcast channel (`server/src/events.rs`), streamed over `/events`. On the client, `useLiveRevalidate` (`app/lib/use-live-revalidate.ts`) reloads the current page's data while a job is running, so pages update without polling. Tabs never read the event payload. This all relies on the server being a single process.

**Playlist editor.** The main screen of the app, at `playlists/:id`. `app/components/playlist/editor-board.tsx` is the whole editor: playlist pane on the left, source browser on the right. The playlist pane virtualises with `@tanstack/react-virtual`, so it renders a flat list of `BoardRow`s (`board-rows.ts`) rather than nested category/channel components; categories, primaries, alternates and auto-group channels are all row kinds in that one flat list. Drag-and-drop uses `@dnd-kit` and is disabled while the playlist filter is active. Edits post to the route's `clientAction` and are handled by `server/src/routes/editor.rs` and `server/src/playlist/mutations.rs`.

**Logic in both halves.** The browser runs alt naming, smart sort (to flag groups worth sorting) and channel matching itself, from `app/lib`. The server has its own copies of alt naming and smart sort. Their tests use the same cases (`test/smart-sort.test.ts`, `server/src/smart_sort.rs`), so change both together.

**Guide.** Each playlist has an in-app EPG grid at `playlists/:id/guide`. `server/src/guide.rs` builds the channel/programme data, `app/components/guide/` renders the grid.

**Backups (`server/src/backup.rs`).** A backup is a gzipped copy of the whole database file. Restore takes a safety backup, brings the backup's schema up to date, then replaces every table. Backups older than the v25 baseline can't be upgraded.

**Logo proxy (`/img`).** Channel logos are proxied through our origin because providers serve them over http (mixed content on an https page) or block hotlinking. Build logo URLs with `app/lib/logo.ts`, don't link provider image URLs directly.

**UI.** Tailwind v4 + shadcn/ui (new-york style) in `app/components/ui/`. Path alias `~` → `app/`. Icons from `lucide-react`.

## Adding a feature

The usual shape of a change, so nothing gets forgotten:

1. Schema change first if needed: a new file in `server/migrations/`, listed in `MIGRATIONS` in `server/src/db.rs`. Comment new tables and columns like the existing ones.
2. Logic in a module under `server/src/`, route handler stays thin.
3. New data for a page? Add it to the page's response struct (with `#[derive(TS)]` and `#[ts(export)]`), run `cargo test` to regenerate `app/api/types`, then use it in the route's `clientLoader`.
4. New page? Add the handler in `server/src/routes/`, declare the page in `app/routes.ts`, then `npm run typecheck`.
5. Tests next to the Rust code. Prefer testing the module, not the route.
6. Add a `CHANGELOG.md` entry (see Notes).
7. If it changed the UI, load it in Safari via the Safari MCP and check it actually works.

## Notes

- **There is no auth.** Every in-app screen is open to anyone who can reach the server. The README tells people to run it on a private network (Tailscale or similar). The output and `/img` routes are public by design.
- Keep `CHANGELOG.md` updated with every feature/fix. It's one running list with no versions, so entries go at the top of the `## Added`, `## Changed` or `## Fixed` section, written as short user-facing prose that explains what changed and why it matters, not commit-style one-liners. Match the tone of the existing entries. Always add new entries, never go back and edit existing ones unless explicitly fixing a mistake.
- Use the Safari MCP to load the app and check UI changes actually work, rather than assuming they do from the code alone.
- SQLite caps bound variables per statement. Pass big id lists with `IN rarray(?)`, or chunk them with `db::ID_CHUNK` where a query needs them as separate values.
